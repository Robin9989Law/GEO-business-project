## 条款 A · 案件级交付清单（最强之一）

**建议写入验收单 / 交付物注册表：**

1. 每一交付行必须带 `{project_id}` / `{client_code}` / `{freeze_id}` / `sop_stage`。  
2. 对照文件只能是：02 验收标准 + `流程/03 测量/案件/{本案}/出数/` 下的现行报告与 `metrics_daily.csv`。  
3. 清单最小集：覆盖（`platforms_required` 齐）、`verdict_4`、`data_grade`、`causal_claim`、禁售句检查、抽检状态。  
4. **禁止**把 `流程/03 测量/出数/`（无案件段）或跨案合并表登记为交付物。

**证据**

| 来源 | 可落地 |
|---|---|
| 06-P39 Xu et al. 2023 质量门 | 质量门是阶段末对照**该门专属验收标准**的决策点；角色+门才能跨部门透明。未过门不得进入下一阶段。 |
| 06-S02 IEEE 828 / 06-S06 ISO 10007 | 配置项必须标识到基线；未标识不得当现行交付。 |
| 06-P10 / 06-P30 / 06-P38 Stage-Gate | 门上只评本阶段允许的产物，不把后一阶段（干预/L1）提前卖进本门。 |
| 06-P25 Enhanced Agile V-Model | 监管域要求可出示的验证/确认交付包，不能用过程故事替代产物。 |
| 06-B01 / 06-B07 UAT checklist | 清单先于演示：范围、角色、通过标准、环境、退出条件。 |

**不要抄：** 把厂商「一键验收」或七家平均可见性表写成交付物；诊断单安排改页。

## 条款 B · 报告校验和（最强之一）

**建议写入验收单：**

1. 验收单登记本案出数目录内每个正式文件的 `sha256`（至少：`metrics_daily.csv`、可见性报告、`verdict_4` 所在页）。  
2. 人审时重算哈希；不一致则**拒收**（材料问题），不得口头说「内容差不多」。  
3. `{freeze_id}` 与 03 冻结 `checksum.txt` 必须一致。  
4. 补件必须生成新哈希并改版本，旧版进 `正式/版本/`，不得覆盖现行。

**证据**

| 来源 | 可落地 |
|---|---|
| 06-P18 Maven-Lockfile 2025 | lockfile 记录版本+checksum，才能重现并检出篡改；只钉直接依赖不够。 |
| 06-P29 SoK 供应链 2024 | 完整性与 provenance 是防御目标；签名/SBOM 采用率低不能当已做。 |
| 06-B17 / 06-B18 / 06-B20 / 06-B24 | 发布完整性、SRI、产物哈希：哈希不匹配即拒绝加载/发布。 |
| 06-S07 NIST SSDF / SLSA | 产物要能核验「就是当时那份」。 |
| 引擎已有实践 | `agent_pm` 对冻结与评审绑定 checksum；06 应对齐同一纪律。 |

**不要抄：** 用截图、聊天转发或「共享盘最新版」代替哈希；把 API 响应当用户所见报告。

## 条款 C · 验收追踪

**建议写入验收单 / 注册表：**

1. 每条 02 验收标准必须能追到 03 出数中的列/页/问法（至少 `p_mention`、覆盖平台、`freeze_id`）。  
2. 追踪是**本案**矩阵，不是跨案总表。  
3. 02 / 03 / 05 三处 `verdict_4` 必须相同；不一致先停门，不解释涨跌。  
4. 诊断只许收「描述基线」或「不能下结论」。

**证据**

| 来源 | 可落地 |
|---|---|
| 06-P07 TOSEM SLR 2025 | 需求驱动测试：需求与测试/评价方法必须对齐；156 项研究的主缺口就是追踪与评价不一致。 |
| 06-P04 机器可读 V&V 规格 2026 | 高层需求落到低层测试，才能回答「这条有没有验」。 |
| 06-P13 TraceTrend / 06-P16 / 06-P19 TVR / 06-P28 NLP RT | 追踪要可验证、可恢复；缺失链路不得宣称覆盖齐全。 |
| 06-P23 汽车感知 RE | 安全关键域用清单+规格+量化质量；缺追踪就补件。 |
| 06-S01 / 06-S04 | V&V 与 29119：验证「做对了」≠ 确认「做了该做的」。 |

**不要抄：** 另做一套可见性表「更漂亮」来补追踪；用监测组当反事实。

## 条款 D · 接收 / 拒收 / 补件（最强之一）

**建议写入 G4 验收单结论栏（三选一，禁止第四态）：**

| 结论 | 条件 |
|---|---|
| **接收** | 覆盖齐；`verdict_4`=03=05；无禁售句；哈希一致；诊断口径未升级 |
| **拒收** | 禁售句；口径放宽；哈希不符；把 API 当用户所见；共享出数目录充交付；试图用结项重开 L1 |
| **补件** | 覆盖缺平台；追踪断；抽检未做；材料版本旧但口径未坏。拒收须写明是覆盖、口径还是材料 |

人签字。Agent 不得 `APPROVE`。G4 通过仍要走 09。

**证据**

| 来源 | 可落地 |
|---|---|
| 06-P39 质量门 | 门主按验收标准决定过 / 不过；黄红不是「差不多过」。 |
| 06-P26 XUAT-Copilot | UAT 目标是对照预定需求决定能否上线；验收工程师对照期望记录缺陷。 |
| 06-P09 / 06-P33 / 06-P34 | UAT 是交付周期最后关；通过标准与退出条件要预先写死。 |
| 06-P11 卫星验收排程 / 06-P24 AAT4IRS | 验收测试有进入/退出准则；未满足则不排下一批。 |
| 06-S03 / 06-S05 | 12207 接收是合同行为；1028 只有通过 / 有条件通过 / 不通过。 |
| 06-B09 / 06-B15 / 06-B16 | 验收标准 ≠ 验收测试；标准先锁，测试后判。 |

**不要抄：** 「客户点头」代替书面三选一；保证推荐或报名因此增长。
