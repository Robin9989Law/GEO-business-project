# GEO 商业项目总体评审与优化方案

归档日期：2026-08-16
来源：项目人员整体评审输入
定位：项目级知识沉淀（不属于某一案件，亦非业务流程文献）
对应行动：分 P0–P3 优先级落到 `合同/`、`流程/`、`agent_pm/`、`工程/`

## 总体判断

系统已经具备可运行的骨架，核心战略和测量原则基本成立：

- 产品线已收敛为诊断、冲刺、续约。
- 主终点固定为无品牌发现问上的 `p_mention`。
- 默认 `descriptive_until_isolation`，确认性 L1 不是默认交付。
- 手机 App 是金标准，API 仅作哨兵并与 App 分表。
- 01→02→07→08→03→04→05→06→09 的行走顺序和文件库 10 已建立。
- G0–G8、原始/正式/中转、冻结配置、校验和、资产脱敏等基础控制已存在。

当前系统已从「搭框架」进入「统一语义、强化门禁、提高可教与可协作性」的阶段。主要风险不是缺少模块，而是同一规则在合同、节点 `AGENT.md`、`agent_pm/agents/`、`guide.py`、模板和引擎中存在少量不同版本。

当前成熟度可概括为：

| 方面 | 现状 |
|---|---|
| 战略线 | 强，核心边界清楚 |
| 技术线 | 强，冻结、App/API、证据身份已成型 |
| 数据线 | 强，但术语和证据等级还需统一 |
| 项目运作线 | 中上，顺序清楚，交付物和审批还需产品化 |
| 人员适配 | 中等，已有 profile 和教学机制，但维度过粗 |
| Agent 协同 | 中等，已有提示词体系，但存在跨文件冲突 |
| 审批审计 | 中等，已有人工门禁，但缺少角色分离和完整门包 |

## 一、四条线的统一逻辑

### 1. 战略线

战略线只回答四件事：

1. 卖哪条产品线：诊断 / 冲刺 / 续约。
2. 解决哪类信息需求：`treat_need_ids` 与 `holdout_need_ids`。
3. 以什么为主终点：`p_mention`。
4. 可以声称到什么程度：四选一与 `causal_claim`。

战略线的输出应形成唯一的「项目战略合同」，由 02 锁定，后续阶段只能读取或收窄，不得重新解释。

### 2. 技术线

技术线回答「如何可靠观察」：

- 冻结词表、平台、别名、事实、环境和产品模式。
- App 冷会话为用户可见金标准。
- API 只作同日哨兵，不能替代 App。
- 每个案件使用独立冻结目录、独立台账和独立出数。
- 所有数据必须带 `case_id / project_id / freeze_id / config_checksum / evidence_run_id`。

### 3. 数据线

数据线回答「如何从样本得到可审计结论」：

- 按 need 等权，而不是按问法条数加权。
- App、API、处理组、监测组、Core、Explore 分表。
- 先测噪声底，再测基线，再决定是否能解释变化。
- 覆盖不全时降级或不能下结论。
- 诊断只输出基线描述。
- 冲刺复测后才产生最终四选一。
- 资产账与项目账分离，客户事实不得进入资产库。

### 4. 项目运作线

项目运作线回答「谁在什么时间，用什么材料，经过什么门」：

```text
战略合同
  → 测量配置冻结
  → 数据证据包
  → 阶段交付包
  → 人工审批
  → 文件版本与资产沉淀
```

四条线的交互规则应固定为：

- 战略线决定技术线可以测什么。
- 技术线决定数据线可以产生什么证据。
- 数据线决定项目运作线可以交付什么结论。
- 项目运作线只负责材料、角色、版本、审批和变更，不得自行扩大测量结论。
- 任何战略变化都必须回到锁定点重新走门，不能通过周报、结项或沟通文件绕过。

## 二、必须优先修正的语义冲突

### P0：统一窗口、四选一和字段所有权

建立一份唯一的阶段字典，至少定义：

| 窗口 | 所属 | 是否可进入 04 计划 | 产出 |
|---|---|---:|---|
| `day0` | 03 | 是 | 冻结、环境登记、试问 |
| `noise` | 03 | 是 | 噪声底 |
| `baseline` | 03 | 是 | 基线与 `baseline_verdict_4` |
| `intervention` | 05 | 是 | 一类证据与干预台账 |
| `wait` | 05 | 是 | 等待期，不采正式复测 |
| `retest` | 05 | 是 | 复测与最终 `verdict_4` |
| `weekly` | 03/续约 | 是 | 滚动监测 |
| `calib` | 03/续约 | 是 | API–App 校准 |

当前文档把「等待窗」「第 0 天」写入计划模板，但引擎允许集合没有对应值；必须统一代码、文档、模板和 guide。

同时统一四选一写入规则：

- 03：诊断/续约写最终 `verdict_4`；冲刺只写 `baseline_verdict_4`。
- 05：冲刺复测后写最终 `verdict_4`。
- 06：抄 03 或 05 的最终值。
- 09：只回声 06，不得重开 L1。

必须修正当前仍存在的冲突：

- `agent_pm/agents/05_control.md` 和 `guide.py` 仍把冲刺周报四选一写成必须等于 03。
- `agent_pm/agents/03_measure.md` 把冲刺最终 `verdict_4`列为 03 可写字段。
- `agent_pm/agents/06_deliver.md` 没有区分诊断与冲刺的四选一来源。
- `02` Agent 提示没有完整列出三套 `success_rule_*`。
- `09` Agent 提示没有说明由引擎自动生成的三个关项字段。

### P0：把战略硬规则真正写入引擎

目前部分规则主要依赖文档，建议把下列值设为硬校验：

- `primary_goal` 必须是统一战略句。
- `primary_endpoint` 必须为 `p_mention`。
- `causal_claim` 默认必须为 `descriptive_until_isolation`，除非经过隔离设计变更。
- `control_design` 默认必须是监测组，且不能被称为反事实。
- 三套 `success_rule_*` 必须与产品线注册表一致。
- `budget_scope` 必须匹配产品线允许集，而不是只检查诊断禁词。
- `platforms_required` 必须与冻结的 `platforms.csv` 一致。
- `treat_need_ids`、`holdout_need_ids` 必须与冻结 `queries.csv` 的集合一致。
- `plan_hours` 与 `budget_hours` 要统一单位，建议统一为「人时」，避免「小时/人天」混用。

### P0：阶段交付物注册化

将现有交付物注册表提升为每个阶段的唯一交付定义。每个阶段必须明确：

- 输入材料。
- Agent 质检结果。
- 正式交付物。
- 证据路径。
- 校验和。
- 完成定义。
- 审批角色。
- 下一站可读取字段。

建议阶段交付表如下：

| 阶段 | 过门前必须存在 | 门上判定 |
|---|---|---|
| 01 / G0 | 商机卡、范围边界、客户原话、禁售已读 | 是否接、接哪条产品线 |
| 02 / G1 | 项目章程、需求规格、验收标准、战略合同快照 | 是否锁定范围与验收 |
| 07 / G6 | 预算、人时拆分、报价排除项 | 是否按平台×问法估算，是否排除 L1 |
| 08 / G7 | 干系人登记、沟通矩阵、对外口径 | 谁听什么，口径到哪 |
| 03 / G3 | 冻结包、环境登记、样本台账、噪声/基线报告、覆盖报告 | 是否可进入计划 |
| 04 / G2 | WBS、进度基线、RACI、风险/依赖 | 是否只排允许窗且不超预算 |
| 05 / G5 | 干预轮次卡、监测组未改证据、等待期、复测包、周报 | 是否完成受控执行 |
| 06 / G4 | 客户交付报告、证据清单、验收单、交付校验和 | 人是否接收 |
| 09 / G8 | 结项报告、经验教训、资产移交、归档清单、中转清空 | 是否真正结案 |

正式发布不应仅凭「文件名以阶段号开头」自动升正式，而应只发布注册表中已声明的 `doc_id`。

## 三、人员适配方案

### 1. 从单一 mode 改为三轴适配

当前 `any_level_is_0 → novice` 的机制容易过度教学。例如 PM 熟练但 GEO 生疏的人，会同时看到大量 PM 解释。

建议保留：

- `pm_level`
- `geo_level`
- `tool_level`

但改为按维度决定讲解深度：

| 能力 | 0 | 1 | 2 |
|---|---|---|---|
| PM | 解释阶段、门、责任 | 给检查清单 | 只给决策差异 |
| GEO | 解释 p_mention、监测组、噪声 | 给指标示例 | 只给异常提醒 |
| Tool | 手把手给路径和命令 | 给命令模板 | 只提示校验结果 |

角色还应独立于能力：

- 负责人：范围、预算、变更、审批。
- 编排：冻结、派单、出数、证据链。
- 操作员：真机采集。
- 评分员：评分与抽检。
- 客户成功：沟通矩阵与接收。
- 资产/文件管理员：版本、中转、封存。

### 2. Guide 的固定输出格式

每一轮只输出：

1. 现在在哪。
2. 当前唯一任务。
3. 人要交什么。
4. 材料放哪。
5. Agent 检查什么。
6. 过门产出是什么。
7. 下一站是什么。
8. 不能做什么。

新手看到白话、示例和反例；熟手看到字段、校验和差异项。路径、门禁和禁止事项不能因熟练度而隐藏。

### 3. 不自动提升能力等级

当前通过两次后自动提高 profile 等级，可能把一次顺利提交误判为真实能力提升。建议：

- 保留表现记录。
- 不自动覆盖用户自报等级。
- 只允许 Agent 调整「本阶段教学深度」。
- 能力升级由人确认或在结项时建议。

## 四、审批与控制优化

### 1. 关键门双角色

采用已确定的「关键门双角色」：

- G1：负责人 + GEO/验收专业复核。
- G3：负责人 + 测量复核。
- G4：负责人/客户成功 + 测量复核。
- G8：负责人 + 文件/资产复核。

G0、G6、G7、G2、G5 可保持单人审批，但必须记录责任角色。

同一成员不得在关键门承担两个签署角色。

### 2. 每个门形成 Gate Packet

每个门的记录至少包含：

```text
gate_id
case_id
stage
required_outputs
hard_check_results
quality_review_id
evidence_checksum
approver_member
approver_role
decision
decision_reason
at
```

`APPROVE` 必须依赖完整 Gate Packet；Agent 只能检查、起草、打回和发布，不能批准。

### 3. CHANGE 变更制度化

`CHANGE` 必须带：

- 变更原因。
- 回退阶段。
- 受影响字段。
- 受影响正式件。
- 受影响测量证据。
- 是否需要重新冻结。
- 是否需要重新预算。
- 是否需要重新沟通确认。
- 作废清单和新版本号。

这样可以把当前已有的 rewind/invalidate 机制变成可解释的变更流程。

## 五、GEO 理念和技术背景的统一表达

新增一份简明术语表，避免以下概念混用：

- `p_mention`：主终点，是否被无品牌发现问正确提及。
- `p_recommend`：次要终点，不等于商业转化。
- App 可见性：用户在手机 App 冷会话中实际观察到的结果。
- API 哨兵：用于日更、校准和异常提示，不是用户所见。
- 监测组：同品类同城的未优化比较对象，不自动等于反事实。
- 噪声底：自然波动，不是效果。
- 受控前后描述：冲刺默认结果，不是确认性因果。
- 确认性 L1：必须有隔离设计、DiD、覆盖和簇数门槛。
- 项目账：服务本案。
- 资产账：只沉淀可迁移结构，不沉淀客户事实。

同时建议避免把「L1」同时用于层级、指标和交付结论；在用户沟通中优先使用完整名称。

## 六、Agent 协作架构

每个阶段应有一份统一的「Agent 合同卡」，字段固定为：

```text
stage
purpose
entry_conditions
read_sources
human_inputs
agent_writable_fields
derived_fields
hard_rules
quality_dimensions
formal_outputs
gate
handoff_to
must_not
```

`流程/*/AGENT.md`、`agent_pm/agents/*.md` 和 `guide.py` 应从同一份规则源校对或生成，避免手工维护三套版本。

每个 Agent 只需要理解四个对象：

1. 当前案件合同字段。
2. 当前阶段输入。
3. 当前阶段输出。
4. 当前门及下一站交接。

跨 Agent 传递不直接依赖聊天内容，而依赖：

- 正式文件版本。
- 中转看板。
- 字段快照。
- 证据身份。
- Gate Packet。

## 七、实施顺序

### P0：语义归一

- 建立窗口、四选一、阶段交付物、字段所有权注册表。
- 修正文档、Agent 提示、guide 与引擎中的冲突。
- 把核心战略常量和预算范围变成硬校验。
- 统一「人时」单位。
- 不改变产品线和 GEO 核心原则。

### P1：门禁和交付产品化

- 引入阶段交付物注册。
- 引入 Gate Packet。
- 加入关键门双角色审批。
- 完善 CHANGE 的影响分析和作废清单。
- 将交付报告、证据清单和正式件版本绑定。

### P2：人员与 Agent 适配

- 将 profile 改为 PM/GEO/Tool 三轴教学。
- 按角色输出任务和权限。
- 建立统一 Agent 合同卡。
- 增加跨文档规则一致性检查。

### P3：验证与试运行

使用三类合成案件验证：

- 诊断：无干预、无 L1、G5 不适用。
- 冲刺：干预、等待、复测、默认受控前后描述。
- 续约：weekly/calib，不重开因果。

再用一个真实案件进行小范围试运行，确认：

- 新手能否只看 guide 推进。
- 熟手能否快速定位差异。
- 不同 Agent 是否引用同一个字段和门。
- 关键门双角色是否不会阻塞正常推进。

## 八、验收测试

必须增加以下测试场景：

1. 非法 `primary_endpoint` 不能过 G1。
2. 诊断计划出现 `intervention` 或 `wait` 不能过 G2。
3. 冲刺在 03 写最终 `verdict_4` 必须失败。
4. 冲刺在 05 未完成等待期不得写最终四选一。
5. `budget_scope` 与产品线不一致必须失败。
6. `platforms_required` 与冻结配置不一致必须失败。
7. 交付目录缺客户报告必须失败。
8. 交付报告身份与冻结身份不一致必须失败。
9. G1/G3/G4/G8 缺第二角色不得批准。
10. 关键门同一成员双签必须失败。
11. CHANGE 后下游正式件和测量证据必须失效。
12. 新手、标准、专家的 guide 必须路径一致、解释深度不同。
13. 诊断、冲刺、续约三条完整路径均能走到 G8。
14. 所有 Agent 提示词中的关键术语与统一注册表一致。

当前 `pytest` 不可用，实施阶段应继续支持现有的直接执行测试方式，并补齐当前工作区已有修改对应的测试夹具。当前 `agent_pm/engine.py` 与 `流程/03 测量/工具/metrics_rollup.py` 存在用户未提交修改，不应回退；应在其基础上补充新的交付报告、证据身份和完整关项测试。

## 默认假设

- 保留诊断 / 冲刺 / 续约三条产品线。
- 保留 `p_mention`、App 冷会话、API 哨兵、监测组非反事实等核心原则。
- 不开发新 App、新后台或新软件系统。
- 优先改造现有合同、模板、Agent 提示、引擎和检查器。
- 关键门采用双角色，其余门保持单人审批。
- 最终成果形态为「总体评审报告 + 分优先级实施清单」，而不是一次性重写全部 SOP。
